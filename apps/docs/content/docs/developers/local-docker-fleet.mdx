The local Docker Fleet is an optional component that manages execution nodes as Docker containers against the same checkout PostgreSQL database as the API. It reuses the existing daemon, runtime, task queue, and report protocol. This page covers the local API integration, the optional managed environment component, the safety rules that govern deletion, the verification gates, and what the setup does not provide.

## Local API integration

Enable local Fleet integration with two variables:

- `MULTICA_LOCAL_FLEET_URL` — the Fleet URL the API calls.
- `MULTICA_LOCAL_FLEET_SECRET_FILE` — the path to a private key file holding the Fleet service key.

The local URL is **mutually exclusive with `MULTICA_CLOUD_URL`**. Setting both fails startup with `local Fleet and SaaS Cloud are mutually exclusive`. Local mode does not enable Cloud Billing, entitlement policy, or strict pre-purchased seat capacity.

The URL is validated on startup:

- Scheme must be `http` or `https`.
- Host must be `localhost` or a loopback IP address.
- No userinfo, no query, no fragment, and the path must be empty or `/`.

The key file is validated on startup:

- An absolute path to a regular file, not a symlink, rechecked against the opened descriptor.
- Owner-readable private permissions: no group or other bits and the owner read bit set (`0600` or `0400`).
- At least 32 bytes and at most 65536 bytes, with no line breaks, after trimming surrounding whitespace.

Local mode creates the Fleet token verifier without a Redis client, which **disables the positive verification cache**. Every node (`mcn_`) token is re-verified against the local Fleet instead of being served from a cache. The internal operation endpoint authenticates the copied service key with a constant-time comparison and rechecks the exact node credential and container identity against SQL.

## Optional managed environment component

The managed environment default stays `api,web`. Opt into the Fleet component explicitly:

```sh
make up C=api,web,fleet
make status
make down
```

- `make down` stops the processes and keeps the data.
- `make destroy` requires explicit confirmation and removes the environment and its data.
- The default `make up` still starts only `api,web`.

The component requires two private inputs, both absolute private paths rather than credential values:

- `MULTICA_FLEET_INPUT` — the private descriptor file.
- `MULTICA_FLEET_OPERATOR` — the private, owner-only Fleet environment operator executable built from `server/cmd/fleet-env`.

`scripts/fleet-env.sh` owns physical provenance and exposes these actions: `prepare`, `up`, `status`, `quiesce`, `down`, and `destroy`.

`prepare` validates the descriptor, verifies the selected Docker Engine, the PostgreSQL container, its compose labels, its published loopback port, its network, and the container-visible Docker socket group, verifies that both images are digest-pinned, refuses a foreign listener on an allocated port, allocates a loopback Fleet port in the `19000`–`20999` range, persists the registry identity, migrates the existing checkout database, and then calls the operator to prepare profiles. There is no second PostgreSQL instance and no public rebind.

The registry persists the managed namespace, Fleet ID, allocated port, and closure (operation) key. Later `status`, `quiesce`, `down`, and `destroy` reuse those saved paths, so the same checkout keeps a stable identity across restarts and other worktrees stay isolated.

Networking is deliberately narrow:

- Fleet joins only the verified shared PostgreSQL Docker network and its own node network.
- Nodes join the node network only and never the PostgreSQL network.
- Only the Fleet port is published, and only on loopback.

Images must be digest-pinned `repository@sha256:...` references. `docker-compose.fleet.yml` sends no checkout build context, and the compose create uses `--no-build`.

The version 1 descriptor declares these fields: `version`, `database_name`, `database_lifecycle`, `context`, `engine_id`, `pg_container_id`, `pg_network_id`, `pg_alias`, `pg_port`, `pg_host_port`, `socket_path`, `uid`, `gid`, `socket_gid`, `node_image`, `fleet_image`, `api_url`, `profiles_file`, and `service_key_file`. It must name the exact registered database (`database_name` must equal the checkout database) and declare `database_lifecycle=exclusive-managed` only after a separate physical ownership preflight. Registry membership is not ownership proof; verify current database identity before any managed database use.

Credential profiles use a strict private map:

```json
{"version": 1, "owners": {"<canonical-nonzero-uuid>": "<absolute-private-path>"}}
```

An empty owner value disables that owner's profile. Credential files must be regular, non-symlink `0600` files owned by the explicit non-root UID, and their directories must be `0700`. `api_url` is the approved `host.docker.internal` API URL and is preserved unchanged.

## Safety and recovery

The Fleet process holds the Docker socket, which is a high-privilege capability. It stays bound to loopback and must never be exposed publicly. Node containers do not receive the Docker socket, do not run privileged, do not use host network or PID namespaces, and run as non-root (`10001:10001`) with `cap_drop: ALL` and `no-new-privileges`.

Defaults are 2 CPU, 4 GiB of memory, 256 PIDs, 1 concurrent run per node, and at most 2 nodes per configured user.

Deletion is permanent and ordered:

- `delete` removes the node container and both of its volumes (data and secrets). Data is removed last, so an uncertain earlier deletion always leaves the data volume for fresh proof and retry.
- The Fleet keeps the API alive until whole-namespace quiesce completes. `make down` and `make destroy` quiesce the namespace before stopping the API, regardless of the component order.
- Busy, unknown-health, or failed cleanup **denies and preserves recovery inputs** (container, volumes, registry, and database). There is no force path; do not improvise one.
- Queued or deferred runs block deletion and must be cancelled before delete. The API returns `409 busy` for active or queued work that must be cancelled first; the Fleet does not silently cancel queued work.
- Pending or failed terminal reports also block deletion, and unknown report proof is reported as `unknown_health`. Failed terminal reports require recovery before cleanup.
- `destroy` requires original SQL completion plus current physical ownership, cleans up resources before database and registry removal, and aborts on failure so the database and registry are kept.

## Verification gates

Default, hermetic checks run without Docker, a database, or any agent CLI lookup:

```sh
bash scripts/fleet-env.test.sh
bash scripts/dev-env.test.sh
```

Docker-backed integration is **opt-in**. The Go integration checks use the `dockerintegration` build tag and skip unless `MULTICA_RUN_DOCKER_INTEGRATION=1` is set. The gate must be checked before any Docker Engine or agent-CLI lookup, so a skipped run never touches the socket:

```sh
(cd server && MULTICA_RUN_DOCKER_INTEGRATION=1 go test -tags=dockerintegration ./internal/fleet/integration -run TestDockerNodeRoundTrip -count=1 -v)
```

The browser `fleet-docker` Playwright project is enabled only under the same `MULTICA_RUN_DOCKER_INTEGRATION=1` gate and is never part of the default suite.

Real agent smoke is separate and requires `MULTICA_RUN_REAL_AGENT_SMOKE=1` with the named `agentintegration` test `TestClaudeFleetRealAgentSmoke`:

```sh
(cd server && MULTICA_RUN_REAL_AGENT_SMOKE=1 go test -tags=agentintegration ./pkg/agent -run '^TestClaudeFleetRealAgentSmoke$' -count=1 -v)
```

The named test is not implemented in this change. Until it is added and separately authorized, its absence or "no tests to run" is setup pending, never a pass.

A skipped test or "no tests to run" is **not** a pass, and a missing environment is setup pending, not a failing test. Run the gated integration and real-model checks only with explicit authorization and the exact named environment.

## What this does not provide

- No per-volume disk quota.
- No physical or cryptographic wipe guarantee.
- No production multi-tenant isolation.
- Docker is a container runtime, not a VM security boundary; node containers are hardened but are not virtual machines.
- No Aurora or AWS deployment. AWS target instance, region, account, and stack overlays require separate, exact authorization and verification.
- This page does not claim that any gated integration or real-model run has been executed or passed.
